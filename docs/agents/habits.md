# Agent Habits

Recurring correction patterns across sessions — check these before diving in.

This file is the **durable source of truth** for agent habits. OpenWiki may regenerate `AGENTS.md` / `CLAUDE.md`; those stubs only point here. Edit this file when a session teaches a new durable habit.

- **Ground truth over speculation.** Before hunting for how something is configured/installed (a plugin, a marketplace, a mechanism), check what's already visible in context (system prompt's skill/package list, settings.json) before searching the filesystem for it.
- **Scope filesystem searches.** Always pass `path`/`maxdepth` (or the `find`/`grep` tool's `path` param) — don't run repo- or filesystem-wide unscoped searches as a first move.
- **Check newly-wired capabilities before falling back to manual work** for an adjacent task — if a skill, tool, or generator was just set up, use it rather than reinventing the adjacent step by hand.
- **Treat live-checkout runs of mutating/regenerating third-party tools** (doc generators, codegen, scaffolders) like destructive git ops: dry-run in an isolated copy, or diff immediately after — never assume success.
- **After bulk path/string rewrites, do a semantic sanity pass** — string replacement can leave sentences that still parse but no longer mean the intended thing; spot-check wording before calling the migration done.
- **Close the loop with real execution output.** Every claim about behavior is backed by a command you actually ran and its pasted output — "I ran X → output Y", never "this should work." Post-edit, run the check/build/test and report the actual result, not the intended one.
- **Label claims by evidence tier.** Distinguish **verified** (ran or read it), **inferred** (deduced from evidence), and **assumed** (no evidence yet). Say "unsure" when unsure — an accurate "I don't know" beats a confident wrong answer. No evidence → cap confidence, don't upgrade a guess to a fact.
- **Read before you describe.** Don't characterize code you haven't opened this session — use `module_report`/`read_symbol`/`read` first. This is the accuracy analog of read-before-edit: cheap grounding, no hallucinated APIs.
- **Compress prose, never compress evidence.** Terse/caveman/ponytail modes strip explanation, hedging, and filler — they must NOT strip the evidence trail. File:line references, command output, and exact error strings stay verbatim; brevity that removes verifiability is a regression.
- **Don't assume POSIX coreutils in agent/non-interactive shells.** `grep`/`find`/`cat` may be shadowed by ripgrep/fd/bat as aliases OR shell functions — not just flag-incompatible (`-E`/`-A`/`-name`/`-maxdepth`), a shadowed `grep` can silently ignore piped stdin (`cmd | grep x` returns nothing, no error). Use `command <bin>` or absolute paths (`/usr/bin/grep`) for anything that must behave POSIX. Note: the ClassDojo dotfiles already removed the `grep=rg`/`find=fd` aliases (verified clean 2026-07-24) — residual breakage is typically the *harness's* captured shell snapshot still defining `function grep`, which agents can't fix; treat this as defensive coding, not a dotfiles bug to chase. **`cp`/`mv` are in the same family:** if aliased to `-i`, an overwrite silently defaults to "no" and the copy/move just doesn't happen (no error) — use `command cp`/`cp -f` when a script depends on the overwrite, and **review the staged diff before committing** as the backstop (this caught a skipped `cp` on 2026-07-24).
- **The `rtk` wrapper rewrites piped `grep` into a repo search — don't pipe command output to bare `grep`.** Distinct from shell aliasing: when `rtk` (or its auto-rewriter) is active, `some-cmd | grep pattern` — especially `gh run view --log | grep …` — gets rewritten into a *repo-wide* grep that ignores the piped stdin, so you get SKILL.md/source matches instead of your command's output (observed repeatedly reading CI logs). Fix: write the output to a temp file first (`gh run view --job <id> --log > /tmp/x.log`) then `command grep`/the grep tool over the file, or use `command grep` in the pipe to bypass the rewriter. Same defensive move as the coreutils-shadowing bullet, different cause.
- **The hypa shell wrapper mangles inline compound bash — put batch logic in a script file.** When pi's `hypa -c` rewriter is active, inline `for` loops, `;`-chained statements, and heredocs get split/garbled (observed: `syntax error near unexpected token`, `hypa: ... process 'do'` — hit twice in one session, whole command silently fails). Don't iterate inline; write the logic to `/tmp/x.sh` and run `bash /tmp/x.sh` (single non-compound invocation the wrapper passes through untouched). Also: **macOS ships bash 3.2** — no `declare -A` (associative arrays silently collapse to one key, producing duplicate/wrong output with no error). Use portable `name|path` line loops (`printf '%s\n' "$pairs" | while IFS='|' read -r a b`) instead.
- **Never `git reset --hard` (or other destructive git) with unrelated uncommitted changes present.** `--hard` wipes working-tree edits to tracked files, and never-staged changes are unrecoverable (no reflog, no dangling blob). Before any destructive git op, run `git status` and `git stash` (or `git stash -u`) the unrelated changes first. To move a commit off a protected branch, use `git reset --soft`/`--mixed` (keeps the working tree) or create the branch *before* committing (`git switch -c`) — `--hard` is almost never the right tool for that.
- **Before any git write (commit/push), verify git env + identity.** Unset or check `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, then confirm `git rev-parse --show-toplevel` and the commit author identity — stale `GIT_*` env vars from a prior session/worktree can silently point commands at the wrong repo. One session nearly committed as the wrong author this way.
- **`gh` account routing is mechanical — the shim handles it.** `~/.local/bin/gh` (source: `dotfiles/.local/bin/gh`, map: `~/.config/gh-accounts.map`) shadows the real `gh` and injects a per-invocation `GH_TOKEN` for personal-mapped owners/hosts, so the mutable active account never matters; `gh auth ...` and pre-set `GH_TOKEN`/`GITHUB_TOKEN` pass through untouched. On a machine without the shim, pin identity per call: `GH_TOKEN=$(gh auth token --user <acct>) gh ...` — never `gh auth switch` (keyring race; see git-guardrails multi-account section).
- **A background subagent's final report is usually swallowed** — the completion `task-notification` arrives with an empty/placeholder `result` (`—`, `(end of task)`, `(end)`) and the actual report never reaches the parent. Don't trust the empty result or re-dispatch the work: recover the report from the agent's transcript output file (`.../tasks/<agentId>.output`, a JSONL) with a *scoped* `jq` — `jq -r 'select(.message.role=="assistant") | .message.content[]? | select(.type=="text") | .text' <file> | tail -120`. Pull only assistant text blocks and tail-limit; never `cat`/`Read` the whole JSONL (it overflows context — the harness warns against it). A `SendMessage` "resend your report" request usually gets swallowed again, so go straight to the transcript. (When dispatching, also recall Explore/read-only agents can't `Write`, so their deliverable must come back through this same channel.)
- **After user pivot, reset the closeout queue.** When a user changes direction mid-session (restarts a workflow, pivots to a different issue, abandons a line of inquiry), discard the queued halt/handoff logic and restate the new active objective in one line before acting. A stale closeout path silently executes after the pivot, reporting completion on the old work instead of the new one.
- **Never suppress mutating command stderr/exit status.** A suppressed error silently no-op's the operation (mkdir, cp, config write, etc.) with no output, and the next check on stale cached state passes. Always capture and check exit status after mutations; re-read authoritative state and confirm the change actually applied before proceeding.
